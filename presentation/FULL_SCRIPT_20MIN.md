## 賴尚圻｜00:00–05:00｜研究動機、資料與網絡定義

[從首頁標題開始。投影停在首頁，讓同學先看到題目。]

大家好，我們是第 J 組。今天的題目是「誰在開源專案裡連接程式碼與社群？」先想像一下，你在使用一個開源工具時碰到錯誤。你可以開一張 Issue 回報，其他帳號可能補充怎麼重現錯誤。接著，有帳號送出一份修改提案，也就是 Pull Request，簡稱 PR。另一個帳號可以對這份修改送出 Review，也就是審查意見。這幾種活動都可能發生在同一個儲存庫，也可能由不同帳號完成。

我們想進一步問，當一個帳號在好幾個儲存庫都留下活動，它在網絡裡會出現在哪些位置？比方說，甲在同一個專案回報很多問題，乙在兩個專案各回報一件。甲的活動筆數比較多，乙則在我們觀察到的關係中跨了兩個專案。要研究跨庫橋接，我們就需要把活動發生在哪裡也記下來。

[點上方「研究問題」，依序指三張卡片。]

我們有三個研究問題。第一，只看 Issue、PR 或 Review 時，排在前面的跨庫橋接帳號是同一批嗎？第二，如果換一把尺，分別看直接連結、最短路徑的位置，以及連結的集中程度，會找出哪些審查帳號？第三，如果從圖上移除排在前面的跨庫帳號，網絡會比隨機移除時更容易分裂嗎？待會我們會在網站上操作這三個分析。

[點「資料範圍」，指向十個儲存庫及事件分類。]

資料來自 GH Archive 的公開 GitHub 事件，透過 ClickHouse 的公開鏡像查詢。時間是二〇二五年一月，從一月一日零時起，到二月一日零時之前，以 UTC 計算。我們選的是 Hugging Face 生態系的十個程式碼儲存庫，例如 Transformers、Datasets 和 Diffusers。同一個生態系讓我們有明確的研究邊界。這十個庫是有目的地選出來的，所以後面每個結論都限定在這些庫和這一個月。

查詢得到 **13,555 筆**事件。我們依帳號名稱過濾可辨識的自動化活動，共排除 **813 筆**，留下 **12,742 筆**，涉及 **1,379 個帳號**。清理是基於可辨識的名稱特徵，資料裡仍可能留有其他自動化帳號。鏡像提供事件發生的時間、儲存庫、觸發帳號和事件種類等欄位。公開紀錄只涵蓋可看到的動作，例如關閉一份 PR 的帳號可能是維護者，PR 作者則是另一個欄位。

網站把事件分成四類。Issue 看議題本身的動作，像是開啟或關閉；PR 看修改提案的動作；Review 包含送出審查以及程式碼審查留言。另外還有一個「討論」層，因為一般留言事件可能出現在 Issue 底下，也可能出現在 PR 底下。這類留言保留在網站，第一題的三層比較則使用 Issue、PR 和 Review。

[點「互動網絡」，選「全部」。指左側儲存庫、右側帳號與中間連線。]

左邊是儲存庫，右邊是帳號。只要一個帳號在某個庫留下過一筆所選類型的事件，兩者之間就連一條線。留一次或十次，這一對帳號和儲存庫都只畫一條。這叫二模網絡，因為節點有兩種類型。像課堂 Davis 的例子把女性與社交活動放在矩陣的兩側，我們也用零和一記錄帳號是否參與過某個庫。

畫面上方的 **93 個跨庫帳號**，是指保留的 1,379 個帳號裡，有 93 個至少參與了兩個庫。右側只畫最多 40 個示例帳號，方便大家看線條。同一個庫連到兩個帳號時，我們只知道兩個帳號都在該庫留下了活動。接下來請第二位組員示範切換事件層，看看橋接名單怎麼變。

## 曹碩顯｜05:00–10:00｜RQ1 不同事件層的橋接者

[留在「互動網絡」。依序點 Issue、PR、Review，每切一次先讓畫面停一下。]

現在我把「全部」切成 **Issue**。右邊亮色而且有編號的帳號，是 Issue 層的橋接榜。看一下排第一的帳號，再切到 **PR**。因為現在只看 PR 事件，第一名改成了 Wauplin。最後按 **Review**，最前面的帳號又換成 LysandreJik。切換時我們保持研究期間和十個儲存庫相同，改的是「哪些事件可以形成一條參與關係」。

[點 Review 圖上一個有編號的帳號，指向右側的參與專案和中介中心度。]

這裡有兩個量可以對照。第一個是 Degree，也就是這個帳號直接連了幾個儲存庫。第二個是 Betweenness，中文叫中介中心度。想像要在圖上由一個端點走到另一個端點，會經過一些最短路徑。如果許多對端點的最短路徑經過同一個帳號，它的中介中心度就會比較高。如果同一對端點有好幾條同樣短的路徑，經過這個帳號的路徑只算其中的比例。這個分數描述圖上的位置，活動筆數則另外顯示。

[點「研究發現」，停在「三層事件的跨庫橋接者」。先指第一張表。]

計算時，每一層都保留十個儲存庫，加上該層至少在兩個庫有活動的帳號。Issue 層有 **23 個**符合條件的跨庫帳號。PR 和 Review 各有 **27 個**。這是各層的二模核心，所以同一個帳號可能出現在其中一層，也可能出現在兩層以上。我們在各層各自計算中介中心度，從正分帳號中取前十名，同分按帳號名稱排序。三層的候選數都足夠，因此每榜實際都取了十位。

還有一個細節。PR 和 Review 的核心剛好同樣有三十七個節點、六十三條邊。如果只看圖有多大，這兩層看起來一樣。可是節點是哪些帳號、每條線連的是哪一個庫，都可能改變。接下來這張表才會告訴我們，同樣大小的兩張圖，榜單究竟有多接近。

[指向第二張表「橋接名單重疊」。先比第一列和第二列，再指第三列。]

有了三份榜單，我們用 Jaccard 相似度回答「重疊到什麼程度」。算法是兩份榜單共有幾個帳號，除以合在一起共有幾個不同帳號。以 Issue 和 PR 為例，各有十位，其中一位兩榜都有，所以合起來是十九位。**一除以十九，大約是零點零五三**。Issue 和 Review 也只有一位共同上榜，所以數值一樣。

PR 和 Review 共有 **四位**，兩份名單的聯集是十六位，所以四除以十六，等於 **零點二五零**。它們在三組比較中重疊最多。把三份名單放在一起看，**沒有帳號同時進入三榜**。因此第一題的答案是，在這個月的跨庫參與裡，橋接位置會隨事件層改變。PR 和 Review 有一部分共用的橋接帳號，但 Issue 的榜單和兩者交集都很小。

[展開「展開三層排名與各層獨有帳號」，只指榜首和下方獨有帳號。]

這裡可以核對三份名單。只在一份榜上出現的帳號，Issue 有八位，PR 和 Review 各有五位。三層的帳號數和路徑結構不同，所以我們用同樣的規則各自排榜，再比較名單的交集。這樣就不用拿兩張不同網絡裡的中介分數直接比大小。

報告下方也保留原本的「參與角色、共同專案與活動量」。例如原有的 Issue 與 PR 的 **0.156**，分母是所有參與這兩類事件的不同帳號，而這一題的 **0.053** 用的是兩份橋接榜單。老師如果問為什麼兩個數字不一樣，可以先看它們各自在比較哪一群帳號。接下來交給第三位組員，看看審查事件能辨識出怎樣的帳號關係。

## 林雨柔｜10:00–15:00｜RQ2 審查互動、中心度與 Constraint

[回到「互動網絡」下方，展開「探索審查者 → PR 作者的互動網絡」。保持預設帳號，指向其中一條箭頭。]

剛才圖上的每條邊都連接一個帳號和一個儲存庫。現在請看這裡的箭頭，兩端都是帳號。這是因為送出 PR 審查的事件可以辨識觸發審查的帳號，也能從同一筆事件取得 PR 作者。我們就以審查者為起點，作者為終點，畫成一條有方向的關係。一般 Issue 或 PR 留言沒有同樣可靠的欄位可一致辨識互動對象，所以這一段使用能辨識的審查關係。

我們先設定篩選條件，排除自己對自己、作者缺漏和可辨識的自動化帳號等情況。最後保留 **2,058 筆**可辨識方向的審查事件，對應 **675 組**不同的「審查者指向 PR 作者」配對。同一組配對可能發生好幾次，在畫面上可看到對應的事件筆數。箭頭的方向來自事件欄位，表示哪個帳號審查了哪個帳號的提案。

[前往「研究發現」的「審查圖上，三種指標找出誰？」。]

接下來三個指標都在同一張圖上算。做法是把有向關係簡化成無向連線。兩個帳號之間只要有一個方向發生過審查，就連一條線。重複審查或雙向審查，在這張簡化圖裡都算同一條。最後有 **375 個帳號、618 條無向邊**。前面 675 組保留審查方向，這裡的 618 條把同一對帳號的兩個方向合在一起。

在這張圖上，**Degree** 數一個帳號有幾個直接相連的審查對象或審查者。**Betweenness** 看它是否常在其他帳號之間的最短路徑上。第三個指標是 **Burt’s Constraint**。想像一個帳號的連線都集中在一群彼此也相連的鄰居，很多路可以在這群鄰居內找到替代。Constraint 用來衡量這種連結集中或重複的程度。分數較低時，表示這個帳號的連線較少集中在相互重疊的關係中，也可能和它有較多鄰居有關。

我們把 Constraint 放在帳號對帳號的審查圖上。回想第一題的二模圖，一個帳號的鄰居全是儲存庫，而儲存庫彼此沒有邊。若直接在那張無權重二模圖計算，Constraint 就只會等於 Degree 的倒數，提供的資訊和 Degree 重複。

[指向散點圖。先指橫軸和縱軸，再指橘點與右側重疊表。]

散點圖每個點代表一個帳號。往右，中介中心度越高。往下，Constraint 越低。橘色帳號同時進入「高中介前十名」和「低 Constraint 前十名」，共有 **九個**。右側表格還顯示，高 Degree 和高中介的兩份榜單共有 **八個**帳號。它們找出的人選相近，仍會出現不同排序。

例如，Degree 首名是 **ArthurZucker**，有 **74 個**直接鄰居。中介中心度首名則是 **aymeric-roucher**，有 **61 個**直接鄰居。同一張圖上，一個帳號可以連到更多鄰居，另一個帳號則在其他節點的最短路徑上具有較高的中介分數。

[展開「展開三個指標榜單與完整帳號表」，指中間的高中介榜和右側低 Constraint 榜。]

再看一個榜單有差異的例子。Wauplin 在中介中心度排第八，但沒有進入低 Constraint 的前十名。如果只用低 Constraint 選帳號，這個最短路徑上的位置就不會出現在榜單裡。這就是第二題的答案。中心度和結構洞指標可以互相補充，幫我們描述多種審查位置。接下來請第四位組員帶大家看移除實驗。

## 粘筑晴｜15:00–20:00｜RQ3 節點移除與結論

[前往「移除帳號後，網絡還連得起來嗎？」。先指基準圖的節點和邊數，再指三種策略的圖例。]

第三題想知道，在全部活動的跨庫網絡裡，如果移除排名靠前的帳號，剩下的節點會不會比隨機移除時更容易分開？這裡我們回到一開始的帳號和儲存庫。基準圖使用全部事件的二模核心，有 **93 個跨庫帳號、10 個儲存庫，共 103 個節點，229 條邊**。

我們比較三種策略。第一種先移除中介中心度最高的帳號，第二種先移除 Degree 最高的帳號，第三種是隨機移除。每種策略都從同一張基準圖出發。兩種排名在原圖先排好，移除後不重新排序。每次只移除帳號和它旁邊的邊，十個庫都保留，即使有庫失去所有連線也一樣。我們分別測試移除一、三、五和十個帳號。隨機策略使用固定種子 **202501**，重複 **500 次**，圖上顯示平均結果和試驗中觀察到的最小、最大值。

[指第一、第二張比例圖，沿著 100% 的水平線由左往右指。]

我們用三個數字看網絡有沒有分裂。第一是連通分量數。只剩一個分量，表示剩下的節點還在同一塊。第二是最大分量比例，分母是剩下的所有節點。第三是可達配對比例，分母是剩餘節點能組成的所有不重複配對，分子是其中還有路可走的配對數。

結果是，在移除一、三、五、十個帳號這四個設定，兩種定向策略都維持 **一個連通分量**，隨機策略的五百次試驗也一樣。兩張比例圖上的線都在 **百分之百**，因為每次移除後，剩下的節點仍能互相到達。

[滑到「同一張圖，移除前與移除後」。把「排名策略」選成「中介優先」、「移除數」選 10，指右圖。再切「Degree 優先」，保持移除數為 10。]

我們實際看一下。中介優先移除十位後，右圖還有 **188 條邊**。改成 Degree 優先後，剩下 **185 條邊**。兩種排名的前十位有七位相同，所以各自移除的帳號並不完全相同。和原來的 229 條邊相比，分別少了 **41 條**和 **44 條**。隨機移除十位平均少了約 **24.66 條**，五百次試驗的範圍是 **20 到 33 條**。

[往上捲回圖表下方，展開「展開各步數的完整數值與固定移除排名」，指一下「庫配對可達」欄。]

如果只關心儲存庫，到底還有幾對庫相互可達？十個庫可以組成四十五個不重複的配對。這一欄一直是百分之百，所以在我們測試的條件下，即使移除的邊比較多，四十五對庫仍然有路可走。只看少了幾條邊會忽略這件事。

[回到「方法與限制」，指向研究範圍或重現資料。]

解讀這個結果時，要把模擬的範圍說清楚。我們在一張由公開事件建出的固定圖上移除最多十個跨庫帳號，量的是移除後是否仍有路可走。現實中如果有人離開，其他帳號可能接手，也可能改變合作方式。那些變化不在圖裡，這次的測試也沒有衡量工作會不會變慢。

最後回到我們的題目。第一，三種事件各有自己的橋接名單，三榜共同入榜的帳號是零。第二，審查圖上高 Degree、高中介和低 Constraint 會指出部分共同帳號，也會找到不同位置。第三，定向移除減少了較多連線，但在我們測試的步數內，剩餘網絡仍然連通。以上是第 J 組的報告，謝謝大家。
